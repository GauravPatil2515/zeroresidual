## ⚡ 1. Mission & Non-Negotiable Tenets

ZeroResidual is an open-source, air-gapped reconciliation engine for Indian merchant settlements. It reconciles **Merchant POS orders**, **Payment Gateway S2S Webhooks**, and **Bank Settlement UTR reports** down to the exact paisa (0.01 INR).

Any AI agent, developer, or automated workflow operating on this repository MUST strictly abide by these five tenets:

### 1. Zero Float Arithmetic (Strict Decimal Precision)
* **Never use Python `float` or JavaScript native IEEE-754 floats for monetary calculations.**
* In Python, all balances, charges, refunds, GST, fees, and residuals **must** use `decimal.Decimal` with string constructors (`Decimal("50000.00")`).
* In JavaScript/TypeScript, format values to 2 decimal places using exact strings or big-decimal utilities.
* If a 1-paisa drift occurs due to float math, the reconciliation engine will reject the run.

### 2. The Honest Residual Guarantee
* When an unexplained variance exists between expected net payout and actual bank credit (e.g., ₹212.00 missing), **the engine must NEVER guess, fabricate, or hallucinate an explanation.**
* It tags the exact amount as `UNEXPLAINED_SHORTFALL` or `UNEXPLAINED_SURPLUS` and terminates with **exit code 1**.
* A clean tie-out (residual = ₹0.00) terminates with **exit code 0**.

### 3. Anti-Hallucination Number Guard (`NumberGuard`)
* When local Google Gemma 2 (2B) generates merchant audit summaries or dispute letters, every monetary value, order ID, and UTR number generated by the LLM is intercepted and verified against an immutable fact sheet.
* If the LLM generates a phantom number (e.g., claiming a ₹500 fee when the fact sheet says ₹423.73), the Number Guard rejects the output and falls back to deterministic templated text.

### 4. Air-Gapped Dual-Mode Architecture
* **Deterministic Fast Path (`--no-llm`):** Runs via regex rules and pluggable bank statement adapters in `< 5ms`.
* **Cognitive Classification Path (Local Google Gemma 2 2B):** Replaces brittle regex with zero-shot classification for cryptic or misspelled bank narrations using an offline, air-gapped local LLM (via Ollama or Llama.cpp).
* **Zero External Network Dependencies:** No external cloud API calls, zero telemetry, full compliance with RBI data localization mandates.

## 🧮 3. Core Reconciliation Math & Invariant

The 3-way reconciliation matches three streams:
1. **POS Orders (`pos_orders.csv`):** Merchant-side successful orders.
2. **Gateway Webhooks (`webhooks.json`):** Payment gateway S2S callbacks (MDR, GST, refunds, disputes).
3. **Bank Statement (`bank_settlement.csv`):** Settlement UTR credits, device rentals, clawbacks.

The fundamental tie-out invariant is:

$$\text{Expected Net Payout} = \text{Gross POS Sales} - \sum \text{Refunds} - \sum \text{Dispute Holds} - \sum \text{T+1 Deferrals} - \sum \text{Gateway MDR} - \sum \text{Hardware/Device Fees}$$

$$\text{Residual Discrepancy} = \text{Expected Net Payout} - \text{Actual Bank UTR Credit}$$

* If $\text{Residual} = 0.00$: **Reconciled (Exit Code 0)**.
* If $\text{Residual} \neq 0.00$: **Unexplained Discrepancy (Exit Code 1)**.

## 🛡️ 4. The Number Guard Verification Pipeline

When local Google Gemma 2 2B generates merchant-facing text:
1. The engine constructs an `ImmutableFactSheet`:
   ```python
   allowed_numbers = {
       gross_pos_sales,
       total_deductions,
       bank_received_payout,
       residual,
       *deduction_breakdowns,
       *order_ids,
       *utr_numbers
   }
   ```
2. The raw text from Gemma is extracted for all currency amounts, floats, and integers using regex.
3. Every extracted number is checked against `allowed_numbers`.
4. If an unauthorized number appears (e.g. Gemma hallucinates a random ₹500 fee), `NumberGuard.verify()` returns `False` and the engine automatically falls back to deterministic, unhallucinated text.
